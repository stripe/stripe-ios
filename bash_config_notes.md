# Configuration, defaults, analytics, loader, and payment-method notes

Scope: source review only; no production or test files edited and no simulator tests run. I read `bug_report_guidance.md` and both current `ISSUE_*.md` reports first.

## Concrete candidate: changing the checkout email does not refresh Link lookup

The documented local-email flow can change the email after Checkout initializes, but the Checkout path only performs Link account lookup during initial load:

- `CheckoutControllerLoader.load` calls `PaymentSheetLoader.loadLink` once, using `session.email ?? configuration.defaults.email` (`CheckoutControllerLoader.swift:44-60`). `PaymentSheetLoader.loadLink` returns `nil` without making a lookup when its supplied email and the Elements Session customer email are absent (`PaymentSheetLoader+Link.swift:104-118`); it then stores that result in `LinkAccountContext.shared.account` (`:25-42`).
- `CheckoutController.updateEmail` commits the new local email through `performUnqueuedUpdate`, then calls `updateForSessionChange` (`CheckoutController.swift:251-260`; `Checkout+Internal.swift:240-267`). The update handler rebuilds and applies both Payment Element configurations, but does not call `loadLink` (`CheckoutControllerLoader.swift:76-190`). The source itself calls this out with `TODO: Refresh Link account lookup when the email changes` (`CheckoutController.swift:256`).
- Link's `.walletButtonHidden` behavior intentionally renders its button only when `LinkAccountContext.shared.account?.isRegistered == true` (`PaymentSheet+PaymentMethodAvailability.swift:96-121`), and `EmbeddedPaymentElement` observes Link-account-context changes to refresh its row (`EmbeddedPaymentElement.swift:444-451`). A session initialized with no email therefore leaves the account context empty after `updateEmail` too; a known Link user who supplies their email later cannot be discovered to make the hidden-wallet row visible. Link signup opt-in eligibility also consults this context (`PaymentSheet+PaymentMethodAvailability.swift:158-174`).

This is a functional candidate, not yet an end-to-end repro. A focused test can configure Checkout's Payment Element with Link `.walletButtonHidden`, initialize a session with neither server email nor default email, then call `updateEmail` with an email whose Link lookup returns a registered user. Assert that a lookup is issued and the registered-user row/eligibility updates. The existing `PaymentMethodAvailabilityTests.testShouldShowLinkButton_linkDisplayWalletButtonHidden_existingUser_buttonShown` covers the visibility predicate, and `PaymentElementTest.testUpdateEmailUpdatesPaymentElementPrefill` covers only the updated form-prefill configuration; there is no Checkout test joining email update to Link lookup/visibility.

## Other checks and ruled-out cases

- **Defaults:** `applyDefaults` stores a default email locally, applies a billing default as a tax-region update when billing is the tax source, normalizes a shipping default through the Shipping Address Element before applying it, validates allowed shipping country, and sets shipping locally even when shipping is not the tax source (`CheckoutController.swift:476-549`). Existing `CheckoutDefaultsInitializationTests` cover email storage, billing/shipping tax requests, normalization, disallowed countries, missing defaults, and missing Address Specs. `PaymentElement.Configuration` forwards billing name/address/phone and email defaults to both Payment Element implementations (`PaymentElement+Configuration.swift`); `Checkout+Session+AddressMerging.swift` then fills missing default email from the latest Session. I found no incorrect default application in these paths.
- **Immutable server email:** The migration guide says `customer_email`/`Customer.email` is immutable and tells merchants not to set `defaults.email` or call `updateEmail`; it says an override returns an error. In release behavior, `canSetLocalEmail()` returns `false` and `updateEmail` exits successfully (the assertion only traps in debug) (`CheckoutController.swift:607-614`, `:251-260`). This is an API/docs mismatch for an explicitly prohibited call, so I did not treat it as a supported-flow bug. The same guard silently ignores `defaults.email` when server email exists, also matching the integration guidance not to supply both.
- **Error handling and guards:** Session mutations serialize through `enqueueSessionUpdate`; API failures preserve the underlying error under `CheckoutError.apiError`; mutations reject a currently presented Payment Element via `requireSheetNotPresented` (`Checkout+Internal.swift:184-267`). Initialization logs the exact configuration and wraps load/default errors with their localized message; empty client secrets get a specific `invalidClientSecret`. The current integration guide tells merchants to display `localizedDescription` for initialization, updates, and confirmation failures, matching these paths. I found no reachable missing error propagation in supported inputs.
- **Payment method eligibility and saved methods:** `CheckoutControllerLoader.handleSessionChange` derives both Payment Element configurations from the same Session, applies the shared `PaymentSheet.PaymentMethodType.filteredPaymentMethodTypes` and `PaymentSheetLoader.filterSavedPaymentMethods` gates, then updates both presentations (`CheckoutControllerLoader.swift:88-190`). The configured `allowsDelayedPaymentMethods` and `allowsPaymentMethodsRequiringShippingAddress` values are enabled for Checkout in both configs. Existing Checkout tests cover saved-card initial selection/tax sync, saved-method selection and rollback on tax-update failure, and both display labels. The TODO for the case where no supported methods remain is explicit and outside this finding; I found no erroneous saved-method filtering in the Checkout wrapper.
- **Express Checkout eligibility:** The wrapper hides Apple Pay unless configured and device-supported, and Link when disabled by session support, Link configuration, billing-tax, required shipping, web Link with required billing collection, or button capacity (`ExpressCheckoutElementUtilities.swift`). The associated `ExpressCheckoutElementViewTests` exercise these gates. Shipping-required and automatic-tax/billing Link exclusions are deliberate and already tested.
- **Analytics/configuration:** Configuration telemetry serializes customer and merchant text only as presence booleans; it serializes safe enum/list values and appearance settings (`Checkout+Analytics.swift`). Existing defaults test asserts this payload. I found no raw email, address, phone, merchant name, or custom removal copy sent in these parameters. Existing `CheckoutDefaultsInitializationTests` also assert the init/address-update lifecycle events and shared analytics session ID.

## Documentation checked

- [Build a checkout with Mobile Checkout Elements](https://docs.corp.stripe.com/payments/mobile/checkout-sessions/build-a-checkout-page): says to use `defaults.email` and `updateEmail` for customer-owned collection/editing, to use Session state as source of truth, and to disable mutation/confirm controls while `isUpdating`.
- [Customize Element appearance](https://docs.corp.stripe.com/payments/mobile/checkout-sessions/customize-appearance): says configure only Elements used; default address values come from `CheckoutController.Configuration.Defaults`, and allowed shipping countries come from the Session.
- [Migrate from Payment Intents](https://docs.corp.stripe.com/payments/mobile/checkout-sessions/migrate-from-payment-intents): documents the immutable server-email rule and current error-display flow; Mobile Checkout Elements supports one-time payments only in this preview.

## Lead verification and narrowed finding

The hidden-wallet eligibility suggestion was not filed. Instead, a real session and real initial Link lookup established that `updateEmail(B)` updates the session and Payment Element config but Link web handoff parameters still contain A. The presentation path does not refresh lookup between `PayWithLinkController.present`, `PayWithLinkWebController.present`, and `LinkURLGenerator.linkParams`. The live repro exercises the actual generator with required Checkout attribution, without opening web UI or confirming a payment. Filed `ISSUE_config_link-web-handoff-keeps-email-before-update.md`; the existing source TODO is disclosed. Initial test omission of attribution caused a trap and was corrected before accepting the failing email assertion.
