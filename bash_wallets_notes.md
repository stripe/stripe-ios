# Wallet confirmation bug-bash notes

Scope reviewed: Checkout confirmation, Apple Pay, and Link under `StripePaymentSheet/StripePaymentSheet/Source/PaymentSheet/Checkout/`, plus existing Checkout confirmation and wallet tests. No production or test files were changed, and no tests were run.

## Reachable confirmation paths

- Merchant `CheckoutController.confirm(from:)` resolves the selected Payment Element option into a normalized flow (`CheckoutController.swift:442-457`, `Checkout+Confirm.swift:144-268`). Express Checkout calls its delegate, builds Apple Pay or Link parameters, then enters the same coordinator (`Checkout+Internal.swift:14-21`; `CheckoutController` extension in that file).
- `confirm(source:makeFlow:)` rejects a closed Session, a duplicate confirmation, and a confirmation while mutations are pending; it queues the complete flow and sets `confirmationInProgress` for its duration (`Checkout+Confirm.swift:272-383`). This keeps a wallet presentation and its callback work inside one serialized operation.
- All standard payment-method, Apple Pay, and Link confirmation results that contain a Checkout response are committed before the coordinator returns. `InternalConfirmResult` carries response payloads on completed, canceled, and failed outcomes (`Checkout+Confirm.swift:116-140, 378-381`). Common `/confirm` handling follows next actions and polls open Sessions; on poll errors it retrieves the latest Session where possible (`:514-641`).

## Apple Pay findings

- Apple Pay presentation is owned by `CheckoutApplePayContext`. Before authorization, cancellation awaits contact-update tasks and restores the original tax region before returning `.canceled` (`CheckoutApplePayContext.swift:164-183, 554-564`). On authorization it tokenizes, changes state to `.pending`, confirms using the token and collected contacts, and reports success/error through PassKit (`:76-146`). While pending, a wallet dismissal is deferred until confirmation resolves to avoid hiding a possibly successful payment (`:164-184`).
- Billing/shipping tax callbacks intentionally use `updateTaxRegionWithoutEnqueueing` because they run inside the enqueued wallet confirmation. The updater documents that it must only be used from an already serialized context (`CheckoutSessionWalletUpdater.swift:8-30`). The known report that this unqueued helper races queued updates is invalid for the production path; see `issue_audit.md`, “Wallet tax update: reject the reported race.”
- A narrow uncovered candidate exists in retry cancellation. A failed authorization sets `paymentState = .error` (`CheckoutApplePayContext.swift:87-96`). A later authorization attempt does not reset that state before tokenization; the next assignment is `.pending`, after tokenization succeeds (`:76-131`). If tokenization is delayed and the customer cancels during that retry, `paymentAuthorizationControllerDidFinish` sees stale `.error`, dismisses immediately, and resumes `self.result` from the previous failed attempt (`:164-184`). The already-completed cancellation-during-tokenization test only covers the initial attempt, where the initial state is `.notStarted` (`CheckoutApplePayContextTests.swift:1008-1033`).

Minimal focused repro to validate this candidate: start the context, complete one authorization with a confirmation failure, start a second authorization with tokenization held by a deferred API client, call `paymentAuthorizationControllerDidFinish`, then release/leave tokenization pending. Observe that the enclosing `presentApplePay()` returns the first `.failed` result instead of `.canceled`; the new attempt's confirmation handler must not run. Existing helpers in `CheckoutApplePayContextTests.swift` can support it, but `DeferredTokenizationAPIClient` currently stores only one completion, so use an immediate token client for attempt one and defer attempt two (or extend the helper to queue completions). The candidate depends on PassKit allowing cancellation during the second tokenization interval; the existing initial-tokenization cancellation test demonstrates that timing window in the same delegate state machine, while the retry test demonstrates that a second authorization occurs after `.error` (`:944-978`). It has no payment-success or double-charge implication.

Recommended focused suite: add the retry-tokenization cancellation case beside `testCancelDuringTokenizationDoesNotConfirm`, retaining the existing retry-success and initial-cancel cases as controls. If the test confirms the stale result, the fix should reset the attempt state/result as soon as each `didAuthorizePayment` starts, before awaiting tokenization; then rerun this trio and the queue/serialization tests.

## Link findings

- Payment Element Link selections and Express Checkout Link selections both enter `confirmLink` inside the confirmation queue. Link may either provide raw payment-method params, a shared/returned PaymentMethod, or call its confirm handler for a wallet result (`Checkout+Confirm+Link.swift:12-27, 72-169`). These routes all use common Checkout request construction and `/confirm`/next-action/poll behavior (`:198-215`). The wallet's final Link result can differ from an earlier failed attempt, so `latestSessionResponse` preserves the most recent response and is attached to the final completed/canceled/failed outcome (`:44-69, 151-168`).
- Existing tests exercise Link decline then close (final result canceled while committing the decline response), decline then retry (final success with the latest response), Link request attribution, and open-session polling (`CheckoutConfirmationStubbedTests.swift:1048-1245`). The nested response propagation paths therefore have direct coverage.
- The `saveForFutureUseCheckboxState` received by the `confirmWithPaymentMethod` callback is not used when constructing a saved-PaymentMethod option (`Checkout+Confirm+Link.swift:104-129`). This appears intentional for an already-created/shared PaymentMethod; the raw-params callback does apply the checkbox (`:72-100`). No concrete user-visible defect was established from this distinction.

## Existing coverage and ruled-out claims

- Duplicate confirmation is covered while `/confirm` is pending, and subsequent session updates are proven to wait behind confirmation (`CheckoutConfirmationStubbedTests.swift:354-407`). A separate test exercises a duplicate during polling (`CheckoutConfirmDuringPollTests.swift`).
- Confirmation response propagation is covered for success, next-action cancellation, and failure after retrieving a PaymentIntent or SetupIntent (`CheckoutConfirmationStubbedTests.swift:212-352`). Poll success, timeout, retrieval failure, and `not_started` paths are also covered in that file.
- Apple Pay covers summary/payment-request construction, allowed/disallowed shipping countries, billing/shipping tax callbacks, cancellation while contact tax updates are pending, serialization against queued merchant updates, authorization details, retry with a fresh token, tokenization failure, and cancellation during first-attempt tokenization (`CheckoutApplePayContextTests.swift`). The live functional test checks a cancel that arrives during in-flight confirmation; the confirmation is allowed to finish (`CheckoutApplePayContextFunctionalTest.swift:63-96`).
- Exclude the old wallet tax race from `ISSUE` consideration: its reproduction called the internal unqueued updater outside the enclosing queue and does not model Apple Pay. Also exclude the earlier presentation-timeout/cancellation report: `issue_audit.md` shows the caller's wait timeout dismisses the picker but does not cancel or orphan the queued confirmation.


## Lead disposition

No issue filed for the retry/cancel result candidate. `STPApplePayContext` uses the same flow-level semantics: after an authorization fails, dismissal reports the recorded error until a subsequent attempt reaches pending or succeeds. Checkout's existing tokenization-failure test explicitly expects that failure on dismissal. A synthetic delegate-order test asserting cancellation would assume a new contract; this review did not establish a PassKit UI failure or a violated API promise. This does not establish that every retry timing is correct.
