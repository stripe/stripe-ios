Summary: A customer who backgrounds/foregrounds the app, or retries payment method selection, while a FlowController confirm is still in its post-`/confirm` poll phase can trigger `CheckoutController.awaitPendingOperations()`'s 30s timeout (hit whenever the merchant calls `flowController.presentPaymentOptions(from:)` again, via `presentPaymentOptionsAwaitingMutations` in `PaymentSheetFlowController.swift:583-618`). When that timeout fires, `PaymentSheetFlowController.swift:606-609` dismisses the loading sheet and calls the completion handler as if everything finished cleanly — but the original confirm (and its `CheckoutSessionPoller.poll()` call) is never canceled and keeps running in the background. It later calls `commitSession`, silently overwriting the shared `@Published session`, possibly after the customer has already picked a different payment method and started a second attempt.

Repro:
1. Start a FlowController confirm whose poll phase takes close to or more than 30s (e.g. a payment method needing 3DS, or a stubbed API client whose `/poll` response stays `confirmation_status: pending`).
2. While that confirm is still polling, call `flowController.presentPaymentOptions(from:)` again (simulates the customer backgrounding/foregrounding, or retrying payment method selection).
3. Wait 30s. `awaitPendingOperations()` throws `.timedOut`; the loading sheet dismisses and `completion(true)` fires as if nothing is pending.
4. Observe that the original confirm/poll keeps running afterward (breakpoint/log on `CheckoutSessionPoller.poll()` or `CheckoutController.commitSession`), and eventually mutates `session` with no UI expecting it.

Test: `StripePaymentSheet/StripePaymentSheetTests/PaymentSheet/Checkout/CheckoutSessionPollerTests.swift` — `testClockSleepIgnoresTaskCancellation`, `testPollKeepsRequestingAfterItsTaskIsCanceled`. These demonstrate the mechanism that lets the orphaned poll keep running once nothing is watching it (see Elaboration); no test yet drives the full `awaitPendingOperations`-timeout-during-a-live-poll path end to end.

Elaboration: Two independent, compounding gaps. The reachable one: `awaitPendingOperations` (`Checkout+Internal.swift:152-172`) wraps the pending operation's `.value` in `withTimeout`, but per `Timeout.swift:58-60`'s own documented contract — "Cancellation does not propagate to unstructured Tasks... you must cancel the task yourself when `withTimeout` throws a `TimeoutError`" — it never calls `.cancel()` on the underlying operation Task when it times out. That's the actual cause of the impact above; I verified no call site anywhere in `Checkout/*.swift` currently does this (grepped for `.cancel()`, `isCancelled`, `checkCancellation`: zero hits). The latent, compounding one: `CheckoutSessionPoller` itself also ignores Task cancellation even if something did try to cancel it — `sleep(for:)` (`CheckoutSessionPoller.swift:25-31`) uses `withCheckedContinuation` + `DispatchQueue.asyncAfter` with no cancellation handling, and the `poll()` loop (`CheckoutSessionPoller.swift:86-154`) never checks `Task.isCancelled`/`Task.checkCancellation()`. This means fixing `awaitPendingOperations` alone (adding a `.cancel()` call on timeout) would not be sufficient — `CheckoutSessionPoller` would ignore that cancellation too, per the two committed tests.
