Summary: The Mobile Checkout Elements integration guide does not explain how to enable merchant-saved payment methods or show them on a returning customer's next checkout. Its email-only Session setup offers no merchant save consent. Passing a Customer alone also leaves saving disabled; the guide omits the additional server configuration.

Repro:

1. Follow the guide's Session setup using `customer_email`, without `customer` or `saved_payment_method_options`. Load Payment Element. Merchant saving is disabled.
2. Replace `customer_email` with an existing Customer ID. Saving remains disabled unless the Session also sets `saved_payment_method_options.payment_method_save` to `enabled`.
3. With both the Customer and that option supplied, opt into saving and complete payment. Create another Session with the same Customer: the saved card appears.
4. The [core guide](https://docs.corp.stripe.com/payments/mobile/checkout-sessions/build-a-checkout-page) and migration guide do not describe this setup or the requirement to reuse the Customer identity. Customer is presented only as an alternative source of email.

Test: `StripePaymentSheet/StripePaymentSheetTests/PaymentSheet/Checkout/CheckoutSavedMethodsGuideLiveTests.swift`: the email-only and Customer-only cases verify saving is disabled; `testExistingCustomerWithSaveOptionPersistsCardForNextSession` verifies real payment confirmation and that a fresh Session for the same Customer exposes the saved card through Payment Element. These three tests passed against the real test backend without mocked responses. The test selects consent through the existing test hook; the earlier saved-card UI test separately exercised the actual checkbox, but used playground-provided server configuration.

The fresh guide-only example-app run also showed [the default card form](images/default-card-link-consent.png): it offers “Save my info for faster checkout with Link,” but no merchant save consent. That visible Link option is not evidence that Customer-based saving has been configured. No Customer or save options were injected for this screen.

Elaboration: `PaymentSheetFormFactory.makeSavePaymentMethodConsentBehavior` requires both `session.customerId` and an enabled server save option. The guide needs a saved-method workflow: create/reuse the app customer's Stripe Customer on the server; pass `customer` instead of the example's `customer_email`; enable `saved_payment_method_options.payment_method_save`; let the customer consent in Payment Element; and use the same Customer on subsequent Sessions. Redisplay eligibility and optional removal controls also need explanation. This concerns saving to the merchant's Customer, not saving to a Link account. The documented private-preview exclusions do not exclude this working flow. Raw guide source checked at docs commit `de7108d190d32c9c7f82b6ae80e8be698f412931` contains none of `payment_method_save`, `customer_creation`, `allow_redisplay`, or `payment_method_remove` under the Mobile Checkout Elements guides.
