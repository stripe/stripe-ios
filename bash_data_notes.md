# Data, currency, and totals bug bash notes

## Call paths verified

- `CheckoutClientAPIResponse.init(from:)` decodes `presentment_currency` as `currency`, rejects an empty code or empty `items`, and rejects any one-time Price item whose `price.currency` differs from the response currency. Each item must provide `unit_amount`, `price.unit_amount`, or a finite `unit_amount_decimal` string. Amount-detail subtotal, total, inclusive tax, exclusive tax, and individual tax amounts are decoded as integer minor-unit amounts.
- `CheckoutController.Session.init(apiResponse:...)` keeps `apiResponse.integrationCurrency` as the public `Session.currency`, sets `presentmentDetails.presentmentCurrency` from `apiResponse.currency` when adaptive pricing data exists, and builds order rows, aggregate totals, and tax rows from the Checkout Client response. The item's currency is therefore the active presentment currency; the integration currency is not used to format the returned line-item values.
- `makeOrderSummaryItems` maps each server-provided amount-detail field and tax amount into public `Session.Amount`. `makeTotals` sums the server-provided per-item subtotal/tax/total values and formats those sums. It does not calculate tax or discounts. `taxAmounts` is mapped separately from server `total_summary.total_tax_amounts`; per-item `amountDetails.taxAmounts` comes from each item. This explains why public aggregate tax rows can exist separately from `totals.taxExclusive` / `totals.taxInclusive`.
- Currency selection calls `CheckoutController.selectCurrency` → queued `.setCurrency` (`adaptive_pricing[currency]`) → `updateCheckoutSession` → `commitSession(response)` → reconstruction of the whole public Session. The selector subscribes to the Session publisher and updates its selected code, localized server totals, and disclosure caption. The selector's displayed amounts use `String.localizedAmountDisplayString`; it does not calculate a conversion rate itself.
- Shipping/tax-region updates likewise use the returned Checkout Client response to reconstruct totals, tax amounts, and presentment metadata. The selected shipping address is local state. For a session whose automatic-tax source is shipping, the network update is `SessionUpdate.setTaxRegion`; the client does not estimate the resulting tax.
- `makeLocalizedPricesMetas` uses Checkout Client amounts for local options and appends the integration currency option if it is absent, with case-insensitive currency comparison. `makeExchangeRateMeta` uses the selected local option, falling back to the first option, and carries server-localized disclosure strings. `CurrencySelectorUtilities` uses those values to build the selector. Flag selection has explicit `ANG → NL` and no-flag handling for XAF/XCD/XOF/XPF; `CheckoutCurrencySelectorViewTests` covers those cases and case normalization. `AdaptivePricingFlagImageManager` clears its cache when the pair is unavailable and falls back to emoji if either image download fails.

## Concrete candidate: formatted public amounts lose cents for Stripe's special two-decimal currencies

`CheckoutClientAPIResponse+Session.swift` converts minor units using `NSDecimalNumber.stp_decimalNumber(withAmount:currency:)`, then formats the major-unit decimal with a fresh `.currency` `NumberFormatter` without setting its fraction-digit count. The Stripe conversion helper explicitly gives COP, PKR, LAK, RSD, IDR, ISK, HUF, and LBP two API decimal places because Foundation treats them as zero-decimal currencies (`StripePayments/.../NSDecimalNumber+Stripe_Currency.swift`). On the current host, a direct Foundation check reports `NumberFormatter.maximumFractionDigits == 0` for COP/IDR/LBP/ISK/HUF while it is 2 for USD and 0 for JPY.

For example, the conversion helper maps 12,345 COP minor units to 123.45 major units, but the formatter configured with `currencyCode = "cop"` emits `COP 123` in the current `en_US` locale. The public `Session.Amount.minorUnitsAmount` remains 12,345, but its customer-facing `amount` string drops the cents. This path is used for public totals, item rows, amount-detail rows, and tax rows. `CurrencySelectorUtilities.makeSelectorItem` calls `String.localizedAmountDisplayString`, whose implementation uses the same default fraction-digit behavior, so adaptive-pricing selector amount labels have the same risk for such currencies.

This is a concrete formatting candidate rather than a wrong server total: all numeric values remain server-derived/correct, while formatted display strings can misstate the value. I did not edit production code or run simulator tests. A focused regression should decode a fixture/session with `presentment_currency` and matching item price currency set to a special two-decimal code (COP is a clear example), use a deterministic locale, and assert that `Session.totals.total.amount` plus a line-item amount preserve two fractional digits; pair it with a JPY case to ensure ordinary zero-decimal formatting stays whole-unit. A currency-selector amount-label case would cover the `String.localizedAmountDisplayString` call path. Existing related coverage checks the numeric conversion of special currencies in `StripeiOS/NSDecimalNumber+StripeTest.swift`, but Checkout response formatting tests only assert USD strings (including the sub-cent USD test).

## Ruled out / scope notes

- `minorUnitsAmountDivisor` uses the same Stripe-aware conversion helper, so the factor is 100 for the special two-decimal currencies, 1 for JPY, and 1,000 for the tested three-decimal currency set. The existing `NSDecimalNumberStripeTest` enumerates these cases. I found no divisor-specific mismatch in the Checkout path.
- Adaptive-pricing totals are not recalculated from raw exchange rates on device. The server supplies each localized currency total, the integration currency amount, and disclosure text; after a currency mutation, the SDK consumes the returned response. Existing `Checkout_AdaptivePricingTests.testAdaptivePricingUsesIntegrationAndPresentmentCurrencies` exercises EUR → USD and asserts the updated presentment code and server total. Selector view tests assert server amount labels refresh when session amounts change.
- Inclusive/exclusive tax classification and amounts are consumed from server response fields. Fixture tests verify item totals/tax detail mapping and aggregation across multiple line items, including inclusive and exclusive taxes. A separate test confirms aggregate tax rows from `total_summary` remain separate from totals.
- Promotion-code discounts are not a supported flow in this Checkout Client surface yet: the public Session conversion has a TODO stating Checkout Client does not expose promotion-code discounts, sets `discountAmounts` to `[]`, and `makeTotals` sets discount to zero. Existing discount-decoding tests are skipped with the same TODO, and Checkout tests mark promo-code behavior unsupported. Treat that omission as known unfinished functionality, not a new bug in this pass.
- Relevant fixture coverage is in `CheckoutClientAPIResponseTest.testDecodedObjectFromAPIResponseMapping`, `testOneTimePriceMapsAmountDetailsPerItem`, `testTotalsSumOneTimePriceItems`, and `testUnifiedModeSessionMapsDecimalOnlyAmountLikeEwCS`. The recorded `CheckoutSession.json` fixture exercises EUR presentment / USD integration, and `Checkout+AdaptivePricingTests.swift` uses a live USD → EUR session. No current Checkout fixture asserts special-currency formatted amount strings.
