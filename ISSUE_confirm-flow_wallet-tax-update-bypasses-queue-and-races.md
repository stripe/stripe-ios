Summary: A merchant integration that shows both a Payment Element and an Apple Pay button (via ExpressCheckoutElement) on the same checkout screen can show the customer a wrong total/tax. If the customer edits their card's billing ZIP in the Payment Element (triggering a billing-tax-region sync) and then taps Apple Pay and picks a shipping contact there (triggering Apple Pay's own tax-region sync) before the first sync's network response has returned, whichever response arrives last wins — even if it's the earlier, now-stale Payment Element update. The customer's later, more relevant Apple Pay-driven tax/total gets silently overwritten by the earlier one.

Repro:
1. Have a `CheckoutController` with both `paymentElement` and `expressCheckoutElement` configured.
2. Start a queued tax-region update for address A (e.g. via `updateBillingTaxRegionIfNecessary`, which goes through `enqueueSessionUpdate`) and let its network request be in flight (don't let it resolve yet).
3. While it's still in flight, call `checkoutWalletUpdater.updateTaxRegionWithoutEnqueueing(address: B, canUpdateWhileSheetPresented: true, confirmationSource: .expressCheckoutElement)` (what Apple Pay's `didSelectShippingContact`/`didSelectPaymentMethod` delegate callbacks call) for a different address B.
4. Let A's response arrive after B's (even though A was sent first and B is the more recent customer action).
5. Observe `checkout.session` reflects A's result, not B's — despite B being requested later.

Test: `StripePaymentSheet/StripePaymentSheetTests/PaymentSheet/Checkout/CheckoutPendingOperationsTests.swift` — `testWalletUpdateBypassesQueueAndCanRaceAQueuedUpdate`. Verified meaningful: temporarily routing the wallet update through the queue (the "fixed" behavior) instead of calling it directly flips the result to the correct one (the later update wins) and makes the test's assertion fail as expected; this was not committed.

Elaboration: `CheckoutSessionWalletUpdater.updateTaxRegionWithoutEnqueueing` (`CheckoutSessionWalletUpdater.swift:34-59`, the only implementation, on `CheckoutController`) calls `performUnqueuedUpdate` directly — it never goes through `enqueueSessionUpdate`/`pendingOperations`, by design (hence the name). But `performUnqueuedUpdate` (`Checkout+Internal.swift:240-271`) carries its own explicit warning: "Only call this within a queued context, to prevent concurrent updates from applying responses out of order." Nothing else compensates for this: `requireSheetNotPresented()` (the only other guard `performUnqueuedUpdate` can check) only looks at `paymentElement?.isPresentingPaymentUI` (`Payment Element/PaymentElement.swift:143-145`), which has no knowledge of an Apple Pay/Express Checkout wallet sheet being open, and the wallet call passes `canUpdateWhileSheetPresented: true` anyway, bypassing that guard regardless. Meanwhile, `updateBillingTaxRegionIfNecessary` (used by Payment Element's billing sync) correctly goes through the FIFO `pendingOperations` queue via `performQueuedUpdate`. So one wallet-adjacent update path respects the queue and the other explicitly doesn't, and nothing prevents both from having requests in flight at once — the two concurrent `/update` network calls can then have their responses arrive in either order, and `commitSession` simply applies whichever one resolves last.
